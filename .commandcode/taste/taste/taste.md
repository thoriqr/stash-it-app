# Taste
- Prefers extending existing architecture over adding new pieces: reuse existing screens, routes, providers, storage keys, DTOs, implementations, shared widgets, existing formatters and existing design tokens (one shared component across call sites instead of duplicated per-screen UI/logic; reuse an existing semantic colour rather than inventing a new token), introducing no new dependency and no duplicate flow ("Do not create a new screen, route, provider, storage key, or dependency", "do not introduce speculative error codes or duplicate DTOs", "do not add a second deletion implementation / duplicate controllers, API methods, or deletion state machines"); an existing action also must not be duplicated as a second affordance elsewhere in the UI — a redundant interactive link next to a price was rejected precisely because a separate Open Original Page action already existed. Obsolete localization keys left behind by a removed string are cleaned up rather than kept. Generated files are regenerated via the existing build_runner workflow and never hand-edited. Confidence: 0.75
- Demands the smallest change that achieves a small visual/layout tweak: inspect the current implementation first, confine the edit to the fewest existing files (presentation only, keeping all behavior, semantics, and disabled states intact), and never redesign, refactor, or introduce a new layout abstraction to get there; unrelated files and pending working-tree changes stay untouched, and no new tests are added for a pure spacing adjustment. Confidence: 0.65
- Prefers analysis and a written implementation plan first; implementation starts only after explicit approval ("stop after presenting the plan and wait for approval before implementation"). Confidence: 0.75
- Wants a plan to end with the decisions and trade-offs that genuinely need their input — the recommended option, why it was chosen, what the alternative would cost, and the accepted limitations — instead of silently picking one and reporting only results. Confidence: 0.6
- Wants verification limited to static and test commands (`format`, `analyze`, test suite) and their genuinely observed results — never launching the app (`flutter run`), running the executable, touching the emulator/device, or committing; manual runtime/UI verification is explicitly reserved for the user themselves ("I will do that myself"), and no tests are added just to substitute for it. A live debug session only happens on an explicit user request that names the exact run command: then start that command verbatim, keep the process alive, avoid restarts and unrelated commands, touch no source files, wait for the user to drive the interaction and report back before reading the logs, and never infer the cause from an error message alone. Confidence: 0.85
- Wants verification reported at its true level: clearly separate what Dart/Flutter tests proved, what a build or resource check proved, and what still requires emulator or physical-device verification — never implying native/runtime behavior was confirmed merely because tests and builds passed, and naming what could not be checked. Confidence: 0.7
- Wants the project's progress document (PROGRESS.md) maintained in place as part of the same uncommitted change: amend and reconcile the existing section so it describes the final state with no contradictory statements, never add a duplicate feature entry, and record only commands/results actually executed after the final changes. Confidence: 0.7
- Prefers fail-fast batch/queue work over partial progress: a sequential operation moves to the next item only after a confirmed success and stops at the first failure — including a per-item validation rejection — leaving the failed item and every unprocessed item intact, instead of continuing past rejections. Confidence: 0.65
- Treats external/deployment values that cannot be derived from the repository (OAuth client IDs, signing SHA-1 fingerprints, bundle identifiers, real credentials) as blockers to report, never to invent: continue everything that can proceed without them and name the exact remaining requirement instead of guessing, and never present third-party sign-in/e2e verification as done when only static and test checks ran. Confidence: 0.7
- Wants user-facing UI copy kept plain, short, and non-technical for ordinary users: everyday wording brief enough to read comfortably where it appears only momentarily (e.g. a Toast), consistent tone across related outcomes, and never any mention of servers, API behavior, interceptors, retries, case-insensitive matching, sessions/access tokens, local persistence, or expiry mechanics — those are implementation details that make an ordinary action sound complicated. Confidence: 0.75
- Wants localized strings built only from complete message units — one complete ARB message per sentence with placeholders and ICU plurals — never sentences assembled by concatenating translated fragments (e.g. a localized "joined" glued to a date, or a count glued to a noun). Confidence: 0.7
- Expects user-facing status copy to be honest about certainty: an outcome that could not be confirmed must be described as unconfirmed, never as a definite failure or definite success, and messages should state plainly what happened to the user's data and where it ended up. Confidence: 0.65
- Allocates storage by sensitivity: non-secret, device-local application data (e.g. locally kept URLs) goes in the existing `shared_preferences` store, while `flutter_secure_storage` stays reserved for credentials and auth continuations — overriding an assistant choice of secure storage for non-secret data unless a concrete technical constraint makes the lighter store unsuitable, without adding a dependency or migrating existing data. Confidence: 0.6
- Rejects speculative or general-purpose infrastructure in a feature: no generic offline queue, automatic retry, background synchronization, or offline-first rearchitecture unless the requested user-visible behavior truly needs it — the simplest mechanism that satisfies the stated UX wins and unrelated functionality stays out of scope. Confidence: 0.6
- Wants actual behavior — of this codebase or of another component (e.g. a sibling backend) — established from its current source code with exact file/method/line references, not from docs, generated specs, endpoint names, or intended design; findings the code proves must be explicitly separated from assumptions, recommendations, and things the code alone cannot establish. Confidence: 0.65
- Prefers stable word values over enum ordinals for persisted preferences/enums, so that reordering or adding variants never breaks an existing installation's restored state. Confidence: 0.85
- Prefers pure, independently testable functions for cross-cutting logic (e.g. locale resolution), receiving platform/device state as a parameter rather than reading framework bindings inside the function itself. Confidence: 0.8
- Expects tests to keep their integrity: existing meaningful assertions are preserved rather than weakened or deleted just to make the suite pass, and new behavior gets genuine coverage (including non-English locales where relevant) instead of assertions being relaxed. Confidence: 0.7
- Gates work per requested stage: complete only the requested fix/phase, stop there, and proceed to the next phase or any further work only after explicit approval ("Stop after this fix. Do not proceed to Phase 2 without explicit approval"). Confidence: 0.7
- Wants a lean, fast test suite over exhaustive coverage in this personal project: tests earn their place by protecting security boundaries, persistence, data integrity, and critical user flows, while presentation-only checks (static copy, labels, rendered properties, per-locale string assertions), trivial getters/wiring, generated behavior, and duplicated coverage across layers are removed aggressively; snapshot, golden, and screenshot tests are ruled out, and anything better confirmed by actually running the app (layout, dimensions, tooltips, cosmetic wiring) is left to manual verification instead of a low-value widget test; localization tests are kept for the mechanism (locale resolution, preference precedence/persistence, formatting, typed-error selection) not for translated copy. Confidence: 0.75
- Keeps the full-suite regression run for themselves: targeted/affected-area tests are run after a change, the whole suite is not launched automatically, and a full pass is never claimed when it was not executed. Confidence: 0.65
- For external/platform research, wants claims grounded in official or primary documentation with source links and each finding explicitly labelled as officially supported, technically possible but unofficial, or unverified — rather than confident guessing where the documentation is silent. Confidence: 0.6
- Wants platform expansion planned portability-first: while adding one target (e.g. Windows) the existing platform must stay unaffected, each platform's requirements are verified independently rather than assumed shared ("Do not assume that configuration required by one platform is also required by another"), and no platform-specific decisions may be made that would complicate a later target (e.g. macOS). Confidence: 0.6
- Insists secrets never surface outside the code that needs them: authorization codes, PKCE verifier/challenge values, client secrets, and provider tokens are never logged, printed, or shown in user-facing copy — including in the machine's own notes and reports ("Use safe diagnostics only. Never print authorization codes, tokens, PKCE verifiers, or client secrets"), and even when a flow is broken the fix must not smuggle a secret into the client or add a server-mediated exchange without explicit approval. Confidence: 0.65
- Prefers coherent implementation stages over excessive task fragmentation: avoid splitting work into unnecessarily tiny tasks in favor of a small number of coherent, independently verifiable stages that each preserve a consistent application state. Confidence: 0.75
- Refuses speculative debugging: the root cause is first established from the actual code path and available diagnostics, an unconfirmed hypothesis is explicitly labelled unverified, and no fix is applied until the failing stage is demonstrated ("Do not guess the root cause or make speculative fixes"). Confidence: 0.7
- Never lets distinct failures collapse into one indistinguishable generic error: where a specific existing error type or message exists it is surfaced, and the failing stage plus safe exception detail are preserved in logs, while loading state and disabled controls are restored after every failure or cancellation. Confidence: 0.65
- Never asks the user to repeat a manual reproduction they already performed: when expected output/evidence is missing, the cause is established from available artifacts (logger sink and whether it reaches the terminal, build/process freshness, captured logs) and stated plainly before any change, with the smallest targeted fix proposed rather than applied. Confidence: 0.65
- Rejects UI-only implementations of user-visible behavior: an action that interrupts or changes an in-flight operation (e.g. Cancel while waiting on an external step such as the browser callback) must reach the underlying operation and release its real resources, with idempotent cleanup and no duplicate completion or state updates after the operation has ended — never a cosmetic state change that only looks like it worked. Confidence: 0.55
- Keeps monetary amounts as text end to end: a decimal amount from the API stays a string through DTO, domain model, mapper and formatter, is never parsed into `double` or subjected to floating-point arithmetic, keeps its exact decimal digits, and is formatted by string manipulation (symbol, thousands grouping, decimal separator) with no new formatting dependency. Confidence: 0.6
- Keeps environment and secret files under their own control: `.env` files and secret values are never edited or created by the agent even when a new variable is required — the code reads the variable, the user adds it manually, and the report confirms that no environment or secret file was touched. Credentials reach the app through build-time configuration the user supplies locally (`--dart-define` read via `String.fromEnvironment`) and are never hardcoded or invented; when a required value is missing the code fails with a clear configuration error before doing any work instead of sending an incomplete request. Confidence: 0.7
- Treats user-authored text as pass-through data: what the user typed is submitted exactly as entered — line breaks, surrounding whitespace and literal characters preserved — and is never trimmed, re-wrapped or otherwise rewritten on the way to the API, while a whitespace-only value is treated as absent (omitted from the request, not sent as an empty string) instead of being silently cleaned. Confidence: 0.7
- Treats Windows and macOS as one desktop target that must share a single layout implementation: identical desktop sizing/alignment behavior expressed through one existing shared condition (e.g. a shared `usesDesktopLayout` getter), never separate per-platform branches or duplicated layout logic, and no new platform abstraction or helper invented just to express it; the desktop rule must also not be keyed off a generic screen-width breakpoint that could leak onto Android, which keeps its own unchanged presentation. Confidence: 0.6
- Keeps the progress document's feature description strictly user-facing: a PROGRESS.md feature entry says what the user can now do, with no test names, test counts, commands, verification logs, or backend/sibling-repository paths and internals — that process detail belongs only in the separate verification record, and existing unrelated history is left intact rather than rewritten. Confidence: 0.6
- Treats an approved design asset as an immutable source of truth: the master file is never overwritten, recompressed, recolored, cropped in place, or replaced by an AI-regenerated/redrawn version (SHA-256 compared before and after to prove it is byte-identical), and every derived artifact is produced by deterministic processing (crop/resample from the measured original, documented recipe) so the change is reproducible and traceable — never reinterpreted artwork or a redrawn approximation. Confidence: 0.7
- Guards the machine's resources: for a task that can be completed by lightweight local means (e.g. deterministic image processing, pixel/metadata inspection, an existing generator invocation), no Flutter command is run at all — no `run`, `build`, `test`, `analyze`, `pub get` or `clean` — and a build is never substituted just because it would give stronger verification; when something cannot be checked under those limits the limitation is reported instead of being worked around with an expensive command. Confidence: 0.7
- Verifies the repository's real structure instead of trusting file paths quoted in a request: example paths in a task description may be stale, so the actual screen/widget/feature locations are found by exploring the codebase first, and the report names the real implementation path when it differs from the one given. Confidence: 0.6
