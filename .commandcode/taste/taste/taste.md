# Taste
- Prefers extending existing architecture over adding new pieces: reuse existing screens, routes, providers, storage keys, DTOs, implementations, shared widgets and existing design tokens (one shared component across call sites instead of duplicated per-screen UI/logic; reuse an existing semantic colour rather than inventing a new token), introducing no new dependency and no duplicate flow ("Do not create a new screen, route, provider, storage key, or dependency", "do not introduce speculative error codes or duplicate DTOs"); generated files are regenerated via the existing build_runner workflow and never hand-edited. Confidence: 0.7
- Demands the smallest change that achieves a small visual/layout tweak: inspect the current implementation first, confine the edit to the fewest existing files (presentation only, keeping all behavior, semantics, and disabled states intact), and never redesign, refactor, or introduce a new layout abstraction to get there; unrelated files and pending working-tree changes stay untouched, and no new tests are added for a pure spacing adjustment. Confidence: 0.65
- Prefers analysis and a written implementation plan first; implementation starts only after explicit approval ("stop after presenting the plan and wait for approval before implementation"). Confidence: 0.75
- Wants a plan to end with the decisions and trade-offs that genuinely need their input — the recommended option, why it was chosen, what the alternative would cost, and the accepted limitations — instead of silently picking one and reporting only results. Confidence: 0.6
- Wants verification limited to static and test commands (`format`, `analyze`, test suite) and their genuinely observed results — never launching the app, touching the emulator/device, or committing. Confidence: 0.8
- Wants verification reported at its true level: clearly separate what Dart/Flutter tests proved, what a build or resource check proved, and what still requires emulator or physical-device verification — never implying native/runtime behavior was confirmed merely because tests and builds passed, and naming what could not be checked. Confidence: 0.7
- Wants the project's progress document (PROGRESS.md) maintained in place as part of the same uncommitted change: amend and reconcile the existing section so it describes the final state with no contradictory statements, never add a duplicate feature entry, and record only commands/results actually executed after the final changes. Confidence: 0.7
- Prefers fail-fast batch/queue work over partial progress: a sequential operation moves to the next item only after a confirmed success and stops at the first failure — including a per-item validation rejection — leaving the failed item and every unprocessed item intact, instead of continuing past rejections. Confidence: 0.65
- Treats external/deployment values that cannot be derived from the repository (OAuth client IDs, signing SHA-1 fingerprints, bundle identifiers, real credentials) as blockers to report, never to invent: continue everything that can proceed without them and name the exact remaining requirement instead of guessing, and never present third-party sign-in/e2e verification as done when only static and test checks ran. Confidence: 0.7
- Wants user-facing UI copy kept plain, short, and non-technical for ordinary users: everyday wording brief enough to read comfortably where it appears only momentarily (e.g. a Toast), consistent tone across related outcomes, and never any mention of servers, API behavior, interceptors, retries, case-insensitive matching, sessions/access tokens, local persistence, or expiry mechanics — those are implementation details that make an ordinary action sound complicated. Confidence: 0.75
- Wants localized strings built only from complete message units — one complete ARB message per sentence with placeholders and ICU plurals — never sentences assembled by concatenating translated fragments (e.g. a localized "joined" glued to a date, or a count glued to a noun). Confidence: 0.7
- Expects user-facing status copy to be honest about certainty: an outcome that could not be confirmed must be described as unconfirmed, never as a definite failure or definite success, and messages should state plainly what happened to the user's data and where it ended up. Confidence: 0.65
- Allocates storage by sensitivity: non-secret, device-local application data (e.g. locally kept URLs) goes in the existing `shared_preferences` store, while `flutter_secure_storage` stays reserved for credentials and auth continuations — overriding an assistant choice of secure storage for non-secret data unless a concrete technical constraint makes the lighter store unsuitable, without adding a dependency or migrating existing data. Confidence: 0.6
- Rejects speculative or general-purpose infrastructure in a feature: no generic offline queue, automatic retry, background synchronization, or offline-first rearchitecture unless the requested user-visible behavior truly needs it — the simplest mechanism that satisfies the stated UX wins and unrelated functionality stays out of scope. Confidence: 0.6
- Wants actual behavior — of this codebase or of another component (e.g. a sibling backend) — established from its current source code with exact file/method/line references, not from docs, generated specs, endpoint names, or intended design; findings the code proves must be explicitly separated from assumptions, recommendations, and things the code alone cannot establish. Confidence: 0.65
- Prefers stable word values over enum ordinals for persisted preferences/enums, so that reordering or adding variants never breaks an existing installation's restored state. Confidence: 0.85
- Prefers pure, independently testable functions for cross-cutting logic (e.g. locale resolution), receiving platform/device state as a parameter rather than reading framework bindings inside the function itself. Confidence: 0.8
- Expects tests to keep their integrity: existing meaningful assertions are preserved rather than weakened or deleted just to make the suite pass, and new behavior gets genuine coverage (including non-English locales where relevant) instead of assertions being relaxed. Confidence: 0.7
- Gates work per requested stage: complete only the requested fix/phase, stop there, and proceed to the next phase or any further work only after explicit approval ("Stop after this fix. Do not proceed to Phase 2 without explicit approval"). Confidence: 0.7
- Wants a lean, fast test suite over exhaustive coverage in this personal project: tests earn their place by protecting security boundaries, persistence, data integrity, and critical user flows, while presentation-only checks (static copy, labels, rendered properties, per-locale string assertions), trivial getters/wiring, generated behavior, and duplicated coverage across layers are removed aggressively; localization tests are kept for the mechanism (locale resolution, preference precedence/persistence, formatting, typed-error selection) not for translated copy. Confidence: 0.7
- Keeps the full-suite regression run for themselves: targeted/affected-area tests are run after a change, the whole suite is not launched automatically, and a full pass is never claimed when it was not executed. Confidence: 0.65
- Prefers coherent implementation stages over excessive task fragmentation: avoid splitting work into unnecessarily tiny tasks in favor of a small number of coherent, independently verifiable stages that each preserve a consistent application state. Confidence: 0.75
